# SnapCore / SnapOCR · 版本规范与记录

> 这份文件是**改版铁律**。任何人接手（包括换人、隔了半年再回来），动代码前先读完它，
> 改完必须在本文件末尾追加一行记录。**不记录 = 没改过**，下一版会被人覆盖掉。

最后更新：2026-11-01 ｜ 当前版本：**C版 v4**

## 一、命名规则（只此一套，不许自创）

| 东西 | 规则 | 例子 |
|---|---|---|
| 交付给用户的 exe | `SnapCore_C版_v{N}.exe` | `SnapCore_C版_v1.exe` |
| 构建产物（内部） | `build/bin/SnapCore.exe` | 同名，不带版本后缀 |
| 源码包 | `SnapCore_C版_v{N}-源码+exe.zip` | `SnapCore_C版_v1-源码+exe.zip` |
| 版本号 | `N` 从 1 起，**只增不减**，每交付一次 +1 | v1 → v2 → v3 |
| 版本记录 | 本文件第七章的表格，追加，不删不改历史行 | — |

**摆放位置**：交付物一律放桌面。桌面只保留**最新一版**的 exe 和源码包，
历史版本留在工程目录 `deliver/v{N}/` 下归档，不要覆盖。

**为什么 exe 名里带版本号**：用户手里可能同时存在多个版本，出了问题要能一眼问出
"你那个是 v2 还是 v3"。文件名就是版本号，不依赖属性页。

## 二、版本叠加规则

1. **永远在上一版的基础上改**，不在旧版上推倒重做。本工程的历史是线性的：
   base12（v1.0 全量修复版）→ v1.2（加文字识别）→ 改名 SnapCore（C版 v1）。
2. **一次交付一个号**。同一天改三处、交付一次，就是 v(N+1)，不写 v2a / v2b / v2-fix。
3. **版本号写进三处**，必须一致：
   - `Src/Res/Resource.rc` 的 `FILEVERSION` / `PRODUCTVERSION` / `FileVersion` / `ProductVersion`
   - `FileDescription` 末尾的 `(C版 v{N})`
   - 本文件第七章表格 + 文件头"当前版本"

   **内部版本号规则**：v{N} 对应 `FILEVERSION = 1,0,0,{N-1}`，
   `FileVersion` / `ProductVersion` 字符串 = `1.0.0.{N-1}`。
   例：v1 → 1.0.0.0，v2 → 1.0.0.1，v3 → 1.0.0.2。
   属性页里能直接看出是第几版的是 `FileDescription` 的「C版 vN」，内部号只是给系统和安装顺序用的。
4. **不改历史**：已经交付出去的 v1、v2 的源码包和记录行，一律不动。
   发现问题就在新版修，然后新增一行说明"修复 v2 的 xxx"。

## 三、改版固定流程（照抄执行）

```bash
cd <工程目录>

# 1) 改代码 / 改文案 / 改资源

# 2) 同步三处版本号（见上）
#    Src/Res/Resource.rc  ← FILEVERSION / FileDescription / ProductVersion

# 3) 构建（约 1 分钟；改过头文件或链接异常时用 clean，约 7 分钟）
./build.sh
#    → build/bin/SnapCore.exe

# 4) 冒烟：双击跑一遍，确认窗口标题是 SnapCore、五页签都在（二维码/文件校验/文件改名/定时关机/设置）
#    模型缓存目录：%LOCALAPPDATA%\SnapCore\ocr（首次识别自动释放，见第四章）

# 5) 交付：复制到桌面并改名
cp "build/bin/SnapCore.exe" "$HOME/Desktop/SnapCore_C版_v{N}.exe"

# 6) 打包源码（与 exe 同一个 zip，命名见第一章），放桌面

# 7) 在本文件第七章追加一行记录 —— 不做这步等于没交付
```

**构建环境注意**（踩过的坑，别重复踩）：

- 用 `build.sh`，不要指望 msbuild（本机安全策略会拦）。脚本自己驱动 cl/link。
- 若出现"构建失败但日志为空"：多半是上次被强杀的 `cl.exe` 还占着 obj 文件。
  `taskkill /F /IM cl.exe` 后重跑。
- `Lang/zh-CN.json` 现为 **UTF-8 无 BOM**（历史是 UTF-16LE，加载器
  `Util::readTextFromBytes` 两种都认，UTF-8 是 JSON 标准，保留现格式即可）。
  用编辑器改它之后，**确认没有被转成 UTF-16 或加 BOM 以外的奇怪编码**。
- 模型资源 32.3MB 打在 exe 里，每次链接都要搬一遍，这是正常的慢。

## 四、改名边界：哪些改、哪些绝对不改

软件名从 SnapCore 改为 **SnapCore**（2026-10-28）。此后新增的呈现层文字一律用 SnapCore。

### 必须改（用户能看见的）

| 位置 | 说明 |
|---|---|
| `Lang/zh-CN.json` → `qr.title` | 主窗口标题 / 托盘提示 / 消息框标题的唯一来源 |
| `Src/Win/WinCap.cpp` → `setTitle(L"SnapCore")` | 截图、录屏窗口标题 |
| `Src/Res/Resource.rc` 版本信息块 | 文件属性页显示的 ProductName / FileDescription |
| `Src/Setting.cpp` 的 MessageBox 标题 | 配置解析失败弹窗 |
| `Src/Setting.cpp` 注册表启动项名 = `SnapCore` | 任务管理器「启动应用」里显示的名字 |
| `Src/Ui/UiApp.cpp` 的 AppUserModelID = `SnapCore` | 任务栏分组 / 通知归属（AUMID 不含空格更稳） |

### 绝对不改（内部标识，改了会出事）

| 标识 | 后果 |
|---|---|
| 窗口类名 `SnapCore_Main` / `SnapCore_Toast` / `SnapCore_VfBox` | `CutMask.cpp` 按类名查找主窗口做"截图时隐藏"，改了找不到窗口 |
| 配置目录 `%APPDATA%\SnapCore\config.json` | 改了 = 老用户全部设置丢失 |
| OCR 缓存 `%LOCALAPPDATA%\SnapCore\ocr` | 改了 = 47MB 模型重新释放一次，首次识别变慢 |
| 环境变量前缀 `SNAPCORE_*` | 调试/构建开关（`SNAPCORE_OCR_EMBED` 等）全部失效 |
| 源码文件结构、`build/obj` 布局 | 增量构建会全量重编，且易触发同名 obj 冲突 |

一句话：**用户看得见的叫 SnapCore，机器看得见的还叫 SnapCore**。这是有意的，不是漏改。

## 五、SnapCore 的固定特征（验收时对照）

- 单 exe，约 32MB，双击即用，无需安装、无需管理员。
- 五个页签，顺序固定：**文字识别 → 二维码 → 文件校验 → 定时关机 → 设置**。
- 默认页是「文字识别」。
- 设置页第二行是「识别快捷键：」——默认文字识别；光标在二维码页时优先二维码，
  没识别到二维码就回落文字识别，并把结果填进二维码输入框生成二维码。
- **按识别快捷键的顺序是固定的**：主界面先收起（不管它当时在不在屏幕上）→ 框选 →
  识别 → 结果填进对应的框 → 界面带着结果弹出。绝不允许"一按热键界面先蹦出来"。
  框选时按 Esc 取消，则回到按键前的状态（原来在前台就恢复前台，原来在托盘就继续待着）。
- 识别快捷键的选区是**常规手动框选**，不做智能选区。
- 文字识别页的「清空」按钮是**红色**。
- 设置页按 `Delete` 清空该行快捷键；点「录入」录制期间，所有已设快捷键暂时失效。
- 首次识别会把模型释放到 `%LOCALAPPDATA%\SnapCore\ocr`（约 47MB），之后复用。
